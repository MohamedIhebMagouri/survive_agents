  # Recovery Metrics Agent

  Cet agent intervient après le Process Capture Agent.

  Le Process Capture Agent :

  1. analyse une description utilisateur ou un formulaire ;
  2. extrait les informations d’un processus ;
  3. retourne un brouillon structuré ;
  4. demande des clarifications si nécessaire ;
  5. permet à l’utilisateur de modifier les champs ;
  6. crée le processus dans la collection `Process` uniquement après confirmation humaine.

  Le Recovery Metrics Agent doit reprendre ce fonctionnement général : il doit analyser, proposer, expliquer, demander
  des clarifications si nécessaire et attendre une validation humaine avant toute approbation définitive.

  Ne réimplémente pas le Process Capture Agent et ne modifie pas son comportement existant sauf nécessité clairement
  justifiée.

  ==================================================
  OBJECTIF
  ==================================================

  Implémente un agent Python capable d’analyser un processus déjà créé et de proposer les objectifs de récupération
  suivants :

  - RTO : Recovery Time Objective ;
  - RPO : Recovery Point Objective ;
  - MTPD : Maximum Tolerable Period of Disruption ;
  - MBCO : Minimum Business Continuity Objective, lorsque les données sont suffisantes.

  Les métriques doivent être cohérentes avec les principes d’ISO 22301 et tenir compte :

  - de la criticité du processus ;
  - des impacts opérationnels ;
  - des impacts financiers ;
  - des impacts réglementaires ;
  - des impacts contractuels ;
  - des impacts réputationnels ;
  - des dépendances internes ;
  - des dépendances IT ;
  - des fournisseurs et partenaires ;
  - de la tolérance à la perte de données ;
  - des activités minimales ;
  - des capacités de reprise connues.

  L’agent ne doit jamais approuver automatiquement une métrique critique.

  ==================================================
  RÈGLE D’ARCHITECTURE
  ==================================================

  Réutilise exactement le pattern du premier agent :

  Next.js API Route
      -> chargement des données Prisma
      -> construction d’un payload JSON
      -> lancement d’un script Python
      -> transmission via stdin
      -> lecture d’un résultat JSON via stdout
      -> validation du résultat côté Next.js
      -> réponse API structurée

  Le nouveau script doit être :

  ```text
  python/recovery_metrics_agent.py

  La nouvelle route principale doit être :

  POST /api/ai/recovery-metrics

  Ne crée pas une architecture indépendante ou incompatible avec celle du Process Capture Agent.

  ÉTAPE 5 — MÉTHODE DE CALCUL

  Implémente une approche hybride :

  1. extraction et interprétation par Gemini ;
  2. règles métier déterministes en Python ;
  3. validation finale côté Python ;
  4. validation supplémentaire côté Next.js.

  Le modèle IA ne doit jamais être utilisé seul pour garantir les contraintes mathématiques.

  ### Contraintes impératives

  0 <= RPO <= RTO <= MTPD

  Les valeurs doivent être exprimées en minutes dans RecoveryObjective.

  ### Calcul du MTPD

  Utilise en priorité :

  - la matrice d’impact BIA ;
  - la première période à partir de laquelle l’impact devient inacceptable ;
  - les obligations réglementaires ;
  - les engagements contractuels ;
  - l’impact financier ;
  - l’impact opérationnel ;
  - les activités minimales.

  ### Calcul du RTO

  Tiens compte :

  - de la criticité ;
  - du MTPD ;
  - du délai avant impact critique ;
  - des dépendances ;
  - de la présence de solutions manuelles ;
  - du niveau minimal de service ;
  - des capacités de reprise connues.

  Heuristiques initiales :

  critical : 60 à 240 minutes
  high     : 240 à 720 minutes
  medium   : 720 à 1440 minutes
  low      : 1440 à 4320 minutes

  Ces intervalles sont des règles de proposition et ne doivent pas être présentés comme des valeurs imposées directement
  par ISO 22301.

  ### Calcul du RPO

  Tiens compte :

  - de la fréquence des transactions ;
  - de la fréquence de mise à jour ;
  - de la perte de données acceptable ;
  - des obligations réglementaires ;
  - de l’existence de réplication ou sauvegardes ;
  - de la capacité de reconstitution manuelle.

  Heuristiques initiales :

  données critiques/réglementées : 0 à 60 minutes
  transactions fréquentes         : 15 à 60 minutes
  activité quotidienne             : 60 à 240 minutes
  activité peu fréquente           : jusqu’à 1440 minutes

  ### Dépendances

  Pour chaque dépendance :

  - identifier son type ;
  - identifier son caractère critique ;
  - évaluer son influence sur le RTO ;
  - signaler les dépendances sans objectif de reprise connu ;
  - générer une question si une dépendance critique est incomplète.

  ### Niveau de confiance

  La confiance doit diminuer lorsque :

  - la criticité est absente ;
  - l’impact est uniquement textuel et non quantifié ;
  - les dépendances sont inconnues ;
  - le rapport BIA est ancien ;
  - les contraintes réglementaires ne sont pas précises ;
  - les valeurs sont principalement inférées.

  ÉTAPE 6 — GESTION DES INCERTITUDES

  Le comportement doit rester cohérent avec le Process Capture Agent.

  Retourne NEEDS_CLARIFICATION lorsque des informations indispensables manquent.

  Retourne HUMAN_REVIEW lorsque :

  - une proposition peut être calculée ;
  - mais son niveau de confiance est inférieur au seuil défini ;
  - ou un impact réglementaire existe ;
  - ou le processus est critical ;
  - ou des dépendances critiques sont incertaines ;
  - ou les métriques proposées diffèrent fortement des valeurs historiques.

  Ne jamais inventer silencieusement :

  - une dépendance ;
  - une obligation réglementaire ;
  - un délai contractuel ;
  - un impact financier ;
  - une capacité technique.

  Chaque valeur doit être classée comme :

  user_input
  bia_report
  business_rule
  ai_inference
  default
  unresolved

  Ajoute les routes :

  Fonctionnement :

  - le calcul IA produit une proposition ;
  - l’utilisateur peut la modifier ;
  - l’utilisateur peut l’approuver ;
  - l’utilisateur peut la rejeter avec une raison ;
  - une nouvelle proposition crée une nouvelle version ;

  Lors de l’approbation :

  RecoveryObjective.status = APPROVED

  Puis, si compatible avec l’existant :

  Process.rto   = approved.rtoMinutes converti en heures
